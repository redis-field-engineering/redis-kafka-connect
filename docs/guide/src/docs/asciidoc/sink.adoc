:name: Sink Connector
[[_sink]]
= {name}

The {name} consumes records from a Kafka topic and writes the data to Redis.

== Class Name

The sink connector class name is `com.redis.kafka.connect.RedisSinkConnector`.

The corresponding configuration property would be:

[source,properties]
----
connector.class = com.redis.kafka.connect.RedisSinkConnector
----

[[_sink_delivery]]
== At least once delivery
The {name} guarantees that records from the Kafka topic are delivered at least once.

[[_sink_tasks]]
== Tasks

The {name} supports running one or more tasks.
You can specify the number of tasks with the `tasks.max` configuration property.

[[_sink_redis_command]]
== Redis Data Structures
The {name} supports the following Redis data-structure types as targets:

* <<_sink_string,string>>
* <<_sink_json,JSON>>
* <<_sink_hash,Hash>>
* <<_sink_hash_field,Hash field>>
* <<_sink_stream,stream>>
* <<_sink_list,list>>
* <<_sink_set,set>>
* <<_sink_zset,sorted set>>
* <<_sink_timeseries,time series>>

=== Redis Keys

Redis keys are generated using the `redis.keyspace` configuration property which may contain `${topic}` (default) as a placeholder for the originating topic name.

For `string`, `json`, and `hash` data structures, the Kafka message key will be appended to the keyspace.
For example, with `redis.type = string`, `redis.keyspace = ${topic}`, a message coming from topic `orders` with a key of `123` will translate into a Redis key of `orders:123`.

Leave the keyspace empty ( `redis.keyspace =` ) if you don't want any key prefix and just use the message key.

For `hash_field`, the value of the record key field selected by `redis.hash.key` is appended to the keyspace instead of the whole key. See <<_sink_hash_field,Hash Field>>.

For `stream`, `list`, `set`, `zset`, and `timeseries` the Redis key is just the keyspace.
For example with `redis.keyspace = set:${topic}` and topic `orders` the Redis key is `set:orders`.

[[_sink_string]]
=== String
Use the following properties to write Kafka records as Redis strings:

[source,properties]
----
redis.type      = STRING
key.converter   = <string or bytes> <1>
value.converter = <string or bytes> <2>
----
<1> <<_sink_key_string,String>> or <<_sink_key_bytes,bytes>>
<2> <<_sink_value_string,String>> or <<_sink_value_bytes,bytes>>.
If value is null the key is deleted.

[[_sink_json]]
=== JSON
Use the following properties to write Kafka records as RedisJSON documents:

[source,properties]
----
redis.type      = JSON
key.converter   = <string, bytes, or Avro> <1>
value.converter = <string, bytes, or Avro> <2>
----
<1> <<_sink_key_string,String>>, <<_sink_key_bytes,bytes>>, or <<_sink_value_avro,Avro>>
<2> <<_sink_value_string,String>>, <<_sink_value_bytes,bytes>>, or <<_sink_value_avro,Avro>>.
If value is null the key is deleted.

[[_sink_hash]]
=== Hash
Use the following properties to write Kafka records as Redis hashes:

[source,properties]
----
redis.type      = HASH
key.converter   = <string or bytes> <1>
value.converter = <Avro or JSON> <2>
----
<1> <<_sink_key_string,String>> or <<_sink_key_bytes,bytes>>
<2> <<_sink_value_avro,Avro>> or <<_sink_value_json,JSON>>.
If value is null the key is deleted.

[[_sink_hash_field]]
=== Hash Field
Use the following properties to write each Kafka record as one field of a shared Redis hash.
Records whose keys share a value (for example a parent ID) are grouped into the same hash, and each record is stored under its own field (for example a child ID):

[source,properties]
----
redis.type       = HASH_FIELD
redis.keyspace   = parent <1>
redis.hash.key   = key.parentId <2>
redis.hash.field = key.childId <3>
key.converter    = <Avro or JSON> <4>
value.converter  = <Avro, JSON, string, or bytes> <5>
----
<1> Optional key prefix. The Redis key is `redis.keyspace` (with `${topic}` replaced), `redis.separator`, then the value selected by `redis.hash.key`, for example `parent:P1`. Leave the keyspace empty to use the selected value alone.
<2> Record key field whose value names the hash.
<3> Record key field whose value names the field within the hash.
<4> The record key must be a Struct (<<_sink_value_avro,Avro>>, or JSON with a schema) or a Map (schemaless JSON).
<5> See <<_sink_hash_field_values,values>> below.

With the configuration above, a record with key `{"parentId": "P1", "childId": "c1"}` is written as `HSET parent:P1 c1 <value>`.

==== Key references
`redis.hash.key` and `redis.hash.field` are both required with `redis.type = HASH_FIELD`, and are not allowed with any other type.
Each one is a reference into the record key, written as `key.<field>`, or `key.<field>.<nested>` for a field inside a nested record.

The referenced value must be a string, a number, a boolean, or bytes.
Numbers and booleans are written as their decimal or `true`/`false` text, and bytes are used as is.
String identifiers are recommended.
Decimals, dates, timestamps, lists, and nested records are not supported as references.

==== Writes, deletes, and ordering
* A record with a value is written with `HSET` to its own field. Other fields in the hash are left unchanged.
* A tombstone (null value) removes only its field with `HDEL`. When the last field of a hash is removed, Redis deletes the hash. A tombstone for a field or hash that does not exist is a no-op.
* Records are applied in Kafka order, so a tombstone that follows a write for the same field in a batch removes it.

[[_sink_hash_field_values]]
==== Values
Struct and Map values are stored as plain JSON (without a schema envelope), and nested records stay nested.
String and bytes values are stored as is.

Values converted to JSON follow the `JsonConverter` encodings: `Decimal` and `bytes` fields are written as base64 strings, `Timestamp` fields as epoch milliseconds, and `Date` fields as days since the epoch.
Consider an {link_smt} if you need a different representation.

[[_sink_hash_field_errors]]
==== Records that cannot be written
A record whose key does not contain the referenced fields cannot be written, for example a plain string key, a missing field, or a referenced field that is null.
Such records are sent to the Kafka Connect errant record reporter instead of being retried, and the standard error handling properties decide what happens next:

[options="header",cols="1,2"]
|====
|Configuration|Behavior
|`errors.tolerance = none` (default)|The task fails. When a dead letter queue or error logging is configured, the record is also written there first.
|`errors.tolerance = all` with `errors.deadletterqueue.topic.name` or `errors.log.enable = true`|The record is written to the dead letter queue or log, and the connector continues with the next record.
|No dead letter queue and no error logging|The task fails.
|====

[WARNING]
====
With `errors.tolerance = all`, a configuration mistake such as the wrong key converter sends every record to the dead letter queue while Redis is left unchanged.
For change data capture topics, where a skipped record leaves stale data in Redis, prefer `errors.tolerance = none`, or monitor the dead letter queue.
Some managed Kafka Connect platforms default to `errors.tolerance = all`, so check the setting for your deployment.
====

==== Per-field TTL
For `HASH_FIELD`, <<_sink_ttl,TTL>> applies to the record's field rather than the whole hash, using the Redis `HEXPIRE` command.
The TTL comes from the record's `redis.key.ttl` header, or from the `redis.key.ttl` configuration property when the record has no header.
Send the header value as decimal text, for example `"3600"`.

* The TTL counts from when the record is written to Redis, not from the Kafka record timestamp, so replaying a topic restarts it.
* Every write sets the field's TTL again. Overwriting a field clears its previous TTL, so a write without a TTL leaves the field without an expiration.
* The hash itself never has a TTL.

`HEXPIRE` requires Redis 7.4 or later, or Valkey 9.0 or later. Support on managed services varies by provider and engine version, so check yours.
The connector checks for `HEXPIRE` support when it starts:

* If `redis.key.ttl` is set and `HEXPIRE` is not supported, the connector fails to start.
* If `HEXPIRE` is not supported, a record with a `redis.key.ttl` header cannot be written and is handled as described in <<_sink_hash_field_errors,Records that cannot be written>>.
* Without any TTL, `HASH_FIELD` works on engines without `HEXPIRE`.

==== Permissions
The Redis user needs the `HSET` and `HDEL` commands (for example ACL `+hset +hdel`), plus `HEXPIRE` (`+hexpire`) when a TTL is used.
If `HEXPIRE` is denied by the ACL, the startup check reports it as not supported. The connector logs the server's response at `INFO`.

[WARNING]
====
Make sure hash keys produced by `HASH_FIELD` do not collide with Redis keys of another type, for example a string written by another connector with the same keyspace.
Redis rejects `HSET` on a key of another type.
====

==== Reading the data
Read all fields of a hash with `HGETALL`, or iterate large hashes with `HSCAN`.
To read your own writes, read from the primary rather than a replica.

[[_sink_stream]]
=== Stream
Use the following properties to store Kafka records as Redis stream messages:

[source,properties]
----
redis.type      = STREAM
redis.keyspace  = <stream key> <1>
value.converter = <Avro or JSON> <2>
----
<1> Stream key
<2> <<_sink_value_avro,Avro>> or <<_sink_value_json,JSON>>

[[_sink_list]]
=== List
Use the following properties to add Kafka record keys to a Redis list:

[source,properties]
----
redis.type     = LIST
redis.keyspace = <list key> <2>
key.converter  = <string or bytes> <3>
----

<1> `LPUSH` or `RPUSH`
<2> List key
<3> <<_sink_key_string,String>> or <<_sink_key_bytes,bytes>>: Kafka record keys to push to the list

The Kafka record value can be any format.
If a value is null then the member is removed from the list (instead of pushed to the list).

[[_sink_set]]
=== Set
Use the following properties to add Kafka record keys to a Redis set:

[source,properties]
----
redis.type     = SET
redis.keyspace = <set key> <1>
key.converter  = <string or bytes> <2>
----
<1> Set key
<2> <<_sink_key_string,String>> or <<_sink_key_bytes,bytes>>: Kafka record keys to add to the set

The Kafka record value can be any format.
If a value is null then the member is removed from the set (instead of added to the set).

[[_sink_zset]]
=== Sorted Set
Use the following properties to add Kafka record keys to a Redis sorted set:

[source,properties]
----
redis.type     = ZSET
redis.keyspace = <zset key> <1>
key.converter  = <string or bytes> <2>
----
<1> Sorted set key
<2> <<_sink_key_string,String>> or <<_sink_key_bytes,bytes>>: Kafka record keys to add to the set

The Kafka record value should be `float64` and is used for the score.
If the score is null then the member is removed from the sorted set (instead of added to the sorted set).

[[_sink_timeseries]]
=== Timeseries
Use the following properties to write Kafka records as RedisTimeSeries samples:

[source,properties]
----
redis.type     = TIMESERIES
redis.keyspace = <key name> <1>
----
<1> Timeseries key

The Kafka record key must be an integer (e.g. `int64`) as it is used for the sample time in milliseconds.

The Kafka record value must be a number (e.g. `float64`) as it is used as the sample value.

[[_sink_value]]
=== Kafka Record Value
Multiple data formats are supported for Kafka record values depending on the configured target <<_sink_redis_command,Redis data structure>>.
Each data structure expects a specific format.
If your data in Kafka is not in the format expected for a given data structure, consider using {link_smt} to convert to a byte array, string, Struct, or map before it is written to Redis.

[options="header",cols="h,1,1"]
|====
|Target|Record Value|Assigned To
|Stream|<<_sink_value_avro,Avro>> or <<_sink_value_json,JSON>>|Message body
|Hash|<<_sink_value_avro,Avro>> or <<_sink_value_json,JSON>>|Fields
|Hash field|<<_sink_value_avro,Avro>>, <<_sink_value_json,JSON>>, <<_sink_value_string,String>>, or <<_sink_value_bytes,bytes>>|Field value (JSON for Avro and JSON)
|String|<<_sink_value_string,String>> or <<_sink_value_bytes,bytes>>|Value
|List|Any|Removal if null
|Set|Any|Removal if null
|Sorted Set|Number|Score or removal if null
|JSON|<<_sink_value_string,String>> or <<_sink_value_bytes,bytes>>|Value
|TimeSeries|Number|Sample value
|====

[[_sink_value_string]]
==== StringConverter
If record values are already serialized as strings, use the StringConverter to store values in Redis as strings:

[source,properties]
----
value.converter = org.apache.kafka.connect.storage.StringConverter
----

[[_sink_value_bytes]]
==== ByteArrayConverter
Use the byte array converter to store the binary serialized form (for example, JSON, Avro, Strings, etc.) of the Kafka record values in Redis as byte arrays:

[source,properties]
----
value.converter = org.apache.kafka.connect.converters.ByteArrayConverter
----

[source,properties]

value.converter                     = io.confluent.connect.avro.AvroConverter

[[_sink_ttl]]
== TTL (Time To Live)

The {name} supports setting TTL (Time To Live) for Redis keys to automatically expire data after a specified duration. TTL can be configured globally for all keys or per-message using Kafka headers.

=== Global TTL Configuration

Set a global TTL for all keys using the `redis.key.ttl` configuration property:

[source,properties]
----
redis.key.ttl = 3600  # TTL in seconds (1 hour)
----

=== Per-Message TTL

Include a `redis.key.ttl` header in your Kafka messages to set TTL for individual records:

[source,java]
----
ProducerRecord<String, String> record = new ProducerRecord<>("topic", "key", "value");
record.headers().add("redis.key.ttl", "1800".getBytes()); // 30 minutes
----

=== TTL Behavior

* TTL is applied using the Redis `EXPIRE` command after data is written
* Per-message TTL headers take precedence over global configuration
* TTL applies to all Redis data types. For `HASH_FIELD`, it applies to the record's field with `HEXPIRE` (see <<_sink_hash_field,Hash Field>>)
* For collection types (STREAM, LIST, SET, ZSET, TIMESERIES), TTL is applied to the collection key
* Invalid TTL values are logged and ignored
* TTL value of -1 (default) means no expiration

[[_sink_config]]
== Configuration

[source,properties]
----
connector.class  = com.redis.kafka.connect.RedisSinkConnector
topics           = <Kafka topic> <1>
redis.uri        = <Redis URI> <2>
redis.type       = <HASH|HASH_FIELD|SET|JSON|STREAM|LIST|SET|ZSET|TIMESERIES> <3>
redis.key.ttl    = <TTL in seconds> <4>
redis.offset.namespace = <Offset namespace> <5>
key.converter    = <Key converter> <6>
value.converter  = <Value converter> <7>
----
<1> Kafka topics to read messsages from.
<2> <<_sink_redis_client,Redis URI>>.
<3> <<_sink_redis_command,Redis command>>.
<4> <<_sink_ttl,TTL in seconds>> (optional, default: -1 for no expiration).
<5> Namespace for sink offset keys stored in Redis (optional, default: connector name).
<6> <<_sink_key,Key converter>>.
<7> <<_sink_value,Value converter>>.
