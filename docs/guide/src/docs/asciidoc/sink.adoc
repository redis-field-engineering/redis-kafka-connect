:name: Sink Connector
[[_sink]]
= {name}

The {name} consumes records from a Kafka topic and writes the data to Redis.

== Class Name

The sink connector class name is `com.redis.kafka.connect.RedisSinkConnector`.

The corresponding configuration property would be:

[source,properties]
----
connector.class = com.redis.kafka.connect.RedisSinkConnector
----

[[_sink_delivery]]
== At least once delivery
The {name} guarantees that records from the Kafka topic are delivered at least once.

[[_sink_tasks]]
== Tasks

The {name} supports running one or more tasks.
You can specify the number of tasks with the `tasks.max` configuration property.

[[_sink_redis_command]]
== Redis Data Structures
The {name} supports the following Redis data-structure types as targets:

* <<_sink_string,string>>
* <<_sink_json,JSON>>
* <<_sink_hash,Hash>>
* <<_sink_hash_field,Hash Field>>
* <<_sink_stream,stream>>
* <<_sink_list,list>>
* <<_sink_set,set>>
* <<_sink_zset,sorted set>>
* <<_sink_timeseries,time series>>

=== Redis Keys

Redis keys are generated using the `redis.keyspace` configuration property which may contain `${topic}` (default) as a placeholder for the originating topic name.

For `string`, `json`, and `hash` data structures, the Kafka message key will be appended to the keyspace.
For example, with `redis.type = string`, `redis.keyspace = ${topic}`, a message coming from topic `orders` with a key of `123` will translate into a Redis key of `orders:123`.

Leave the keyspace empty ( `redis.keyspace =` ) if you don't want any key prefix and just use the message key.

For `stream`, `list`, `set`, `zset`, and `timeseries` the Redis key is just the keyspace.
For example with `redis.keyspace = set:${topic}` and topic `orders` the Redis key is `set:orders`.

For `hash_field`, the value selected by `redis.hashfield.hash` from the Kafka message key is appended to the keyspace instead (see <<_sink_hash_field,Hash Field>>).

[[_sink_string]]
=== String
Use the following properties to write Kafka records as Redis strings:

[source,properties]
----
redis.type      = STRING
key.converter   = <string or bytes> <1>
value.converter = <string or bytes> <2>
----
<1> <<_sink_key_string,String>> or <<_sink_key_bytes,bytes>>
<2> <<_sink_value_string,String>> or <<_sink_value_bytes,bytes>>.
If value is null the key is deleted.

<1> <<_sink_key_string,String>>, <<_sink_key_bytes,bytes>>, or <<_sink_value_avro,Avro>>
<2> <<_sink_value_string,String>>, <<_sink_value_bytes,bytes>>, or <<_sink_value_avro,Avro>>.

[[_sink_stream]]
=== Stream
Use the following properties to store Kafka records as Redis stream messages:

[source,properties]
----
redis.type      = STREAM
redis.keyspace  = <stream key> <1>
value.converter = <Avro or JSON> <2>
----
<1> Stream key
<2> <<_sink_value_avro,Avro>> or <<_sink_value_json,JSON>>

[[_sink_list]]
=== List
Use the following properties to add Kafka record keys to a Redis list:

[source,properties]
----
redis.type     = LIST
redis.keyspace = <list key> <2>
key.converter  = <string or bytes> <3>
----

<1> `LPUSH` or `RPUSH`
<2> List key
<3> <<_sink_key_string,String>> or <<_sink_key_bytes,bytes>>: Kafka record keys to push to the list

The Kafka record value can be any format.
If a value is null then the member is removed from the list (instead of pushed to the list).

[[_sink_set]]
=== Set
Use the following properties to add Kafka record keys to a Redis set:

[source,properties]
----
redis.type     = SET
redis.keyspace = <set key> <1>
key.converter  = <string or bytes> <2>
----
<1> Set key
<2> <<_sink_key_string,String>> or <<_sink_key_bytes,bytes>>: Kafka record keys to add to the set

The Kafka record value can be any format.
If a value is null then the member is removed from the set (instead of added to the set).

[[_sink_zset]]
=== Sorted Set
Use the following properties to add Kafka record keys to a Redis sorted set:

[source,properties]
----
redis.type     = ZSET
redis.keyspace = <zset key> <1>
key.converter  = <string or bytes> <2>
----
<1> Sorted set key
<2> <<_sink_key_string,String>> or <<_sink_key_bytes,bytes>>: Kafka record keys to add to the set

The Kafka record value should be `float64` and is used for the score.
If the score is null then the member is removed from the sorted set (instead of added to the sorted set).

[[_sink_timeseries]]
=== Timeseries
Use the following properties to write Kafka records as RedisTimeSeries samples:

[source,properties]
----
redis.type     = TIMESERIES
redis.keyspace = <key name> <1>
----
<1> Timeseries key

The Kafka record key must be an integer (e.g. `int64`) as it is used for the sample time in milliseconds.
A key of `0` requests the Redis server's current timestamp, preserving the previous LettuceMod behavior.

The Kafka record value must be a number (e.g. `float64`) as it is used as the sample value.

[[_sink_hash_field]]
=== Hash Field
Use the following properties to write each Kafka record as one field of a shared Redis hash.
This suits topics that carry changes to individual items of a group, keyed by a structured key that names both the group and the item:

[source,properties]
----
redis.type            = HASH_FIELD
redis.keyspace        = parents <1>
redis.hashfield.hash  = key.parentId <2>
redis.hashfield.field = key.childId <3>
key.converter         = <Avro, JSON Schema, Protobuf, or schemaless JSON> <4>
----
<1> Prefix of the hash name (optional, default: `${topic}`). Leave it empty to name the hash by the key value alone.
<2> Field of the record key that names the destination hash, written as `key.<field>` or `key.<field>.<nested>`.
The hash is named `<redis.keyspace><redis.separator><value>`, for example `parents:p1`.
<3> Field of the record key that names the field within the hash, using the same syntax. The value is used as is, with no prefix.
<4> The record key must be a Struct or a map.

For a record with the key `{"parentId": "p1", "childId": "c1"}`:

* a record value runs `HSET parents:p1 c1 <value>`
* a null value (tombstone) runs `HDEL parents:p1 c1`, removing only that field
* a <<_sink_ttl,TTL>> expires the whole hash, and an optional <<_sink_hash_field_expiry,field TTL>> expires only that field

Readers can then use `HGETALL parents:p1` for every item of `p1` and `HGET parents:p1 c1` for one item.

Only the record key needs to be structured. The record value is stored as follows:

* bytes (<<_sink_value_bytes,ByteArrayConverter>>) and strings (<<_sink_value_string,StringConverter>>) are stored unchanged.
For example, the byte array converter keeps a Schema Registry–encoded Avro value in its original wire format.
* any other value, such as a Struct or map read with <<_sink_value_avro,Avro>> or <<_sink_value_json,JSON>>, is stored as a JSON document.

Record keys do not need a schema registry. JSON keys work with the schemaless JSON converter:

[source,properties]
----
key.converter                = org.apache.kafka.connect.json.JsonConverter
key.converter.schemas.enable = false
----

The referenced key fields can be strings, booleans, numbers or bytes.
Decimal fields are written in plain notation without trailing zeros, so `12.500` and `12.5` name the same hash.

A record whose key does not contain the configured fields is invalid record data: the batch fails before any command is sent.

Multiple data formats are supported for Kafka record values depending on the configured target <<_sink_redis_command,Redis data structure>>.
Each data structure expects a specific format.
If your data in Kafka is not in the format expected for a given data structure, consider using {link_smt} to convert to a byte array, string, Struct, or map before it is written to Redis.

[[_sink_ttl]]
== TTL (Time To Live)

The {name} supports setting TTL (Time To Live) for Redis keys to automatically expire data after a specified duration. TTL can be configured globally for all keys or per-message using Kafka headers.

=== Global TTL Configuration

Set a global TTL for all keys using the `redis.key.ttl` configuration property:

[source,properties]
----
redis.key.ttl = 3600  # TTL in seconds (1 hour)
----

=== Per-Message TTL

Include a `redis.key.ttl` header in your Kafka messages to set TTL for individual records:

[source,java]
----
ProducerRecord<String, String> record = new ProducerRecord<>("topic", "key", "value");
record.headers().add("redis.key.ttl", "1800".getBytes()); // 30 minutes
----

=== TTL Behavior

* TTL is applied using the Redis `EXPIRE` command after data is written
* Per-message TTL headers take precedence over global configuration
* TTL applies to all Redis data types
* For collection types (STREAM, LIST, SET, ZSET, TIMESERIES), TTL is applied to the collection key
* For HASH_FIELD, TTL is applied to the hash key, so it expires every field of the hash. To expire individual fields, see <<_sink_hash_field_expiry,Hash Field Expiry>>.
* Invalid TTL values are logged and ignored
* TTL value of -1 (default) means no expiration

[[_sink_hash_field_expiry]]
=== Hash Field Expiry

With `redis.type=HASH_FIELD`, each field can also expire on its own, using the Redis `HEXPIRE` command:

[source,properties]
----
redis.hashfield.hexpire.enabled = true <1>
redis.hashfield.hexpire.ttl     = 3600 <2>
----
<1> Enables field expiry (optional, default: `false`).
<2> TTL in seconds for the record's field (optional, default: -1 for no expiration). Requires `redis.hashfield.hexpire.enabled=true`.

Include a `redis.hashfield.hexpire.ttl` header in your Kafka messages to set the field TTL for individual records:

[source,java]
----
ProducerRecord<String, String> record = new ProducerRecord<>("topic", key, value);
record.headers().add("redis.hashfield.hexpire.ttl", "1800".getBytes()); // 30 minutes
----

* The header takes precedence over the configured field TTL.
With field expiry enabled and no configured field TTL, only records with the header expire.
* A header value of 0 or below means no expiry for that record, even when a field TTL is configured.
* If a record has several headers with this name, the last one wins.
* The header value can be a string, a number or bytes; bytes are read as text in the configured charset.
* The field TTL can be at most 4611686018427387 seconds, in the configuration and in the header.
* `redis.key.ttl` and the field TTL can be combined.
The key TTL expires the whole hash and the field TTL expires only the record's field; both are reset on every write.
* Each write replaces the field and clears its previous TTL, so a record without a field TTL leaves its field without expiration.
* A tombstone removes the field and sets no TTL.
* Field expiry requires a Redis server that supports `HEXPIRE`, for example Redis 7.4 or later.
When it is enabled, the task checks at startup by calling `HEXPIRE` on the key `__redis-kafka-connect-hexpire-probe`, which does not exist, so nothing is written.
If the server does not support `HEXPIRE`, the task fails to start with an error saying so.
If the check fails for another reason, such as missing permissions, the task fails to start with the server's error.
The connector's user needs permission to run `HEXPIRE` on the destination keys and on that key.
* While field expiry is disabled, `redis.hashfield.hexpire.ttl` headers are ignored, so turning it off stops field expiry without rewriting the topic.
* While field expiry is enabled, a header value that is not a number or is above the maximum makes the record invalid: the batch fails before any command is sent.

[[_sink_config]]
== Configuration

[source,properties]
----
connector.class  = com.redis.kafka.connect.RedisSinkConnector
topics           = <Kafka topic> <1>
redis.uri        = <Redis URI> <2>
redis.type       = <HASH|HASH_FIELD|SET|JSON|STREAM|LIST|SET|ZSET|TIMESERIES> <3>
redis.key.ttl    = <TTL in seconds> <4>
redis.offset.namespace = <Offset namespace> <5>
key.converter    = <Key converter> <6>
value.converter  = <Value converter> <7>
----
<1> Kafka topics to read messsages from.
<2> <<_sink_redis_client,Redis URI>>.
<3> <<_sink_redis_command,Redis command>>.
<4> <<_sink_ttl,TTL in seconds>> (optional, default: -1 for no expiration).
<5> Namespace for sink offset keys stored in Redis (optional, default: connector name).
<6> <<_sink_key,Key converter>>.
<7> <<_sink_value,Value converter>>.

== Batching, Transactions, and Retries

Commands affecting the same key retain input order, including tombstones and TTL updates.
The task waits for every command result before accepting the batch. Invalid record data
fails before any commands in that batch are sent. Server errors and partial failures can
still occur after some commands have executed; replay can duplicate list entries, stream
messages, or other non-idempotent operations. Delivery remains at least once.

`redis.multiexec=true` keeps one transaction per batch with `redis.cluster=false`, preserving
atomic execution across its keys on standalone Redis. `redis.wait.replicas` waits for
replication on that connection after its writes and fails the batch if the configured
acknowledgment target is not reached. WAIT is not a guarantee against all failover data loss.
Both transactions and WAIT are rejected when `redis.cluster=true`. Cluster writes use
Lettuce's asynchronous routing, pipelining, and redirect handling without per-slot transactions
or per-primary replication waits. Sharded Enterprise proxies must support the requested
transaction themselves; the connector does not split transactions across shards.
Offset keys are persisted after successful writes and keep their existing namespace and JSON format.
